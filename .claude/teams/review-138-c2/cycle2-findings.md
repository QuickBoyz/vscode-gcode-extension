## New Findings (from cycle-1 fix diff only)

- `src/server/server.ts:272` | `progressFactory` bypasses `_progressSupported` flag | P3 | 0.65 | The new code sends `WorkDoneProgressCreateRequest` unconditionally and relies on `catch {}` to return `undefined` if the request fails. `connection.window.createWorkDoneProgress()` (original) gates on `_progressSupported` and returns a `NullProgressServerReporter` immediately when unsupported — no IPC round-trip. The new approach is functionally safe (the catch returns `undefined`; all `progress?.xxx` calls no-op via optional chaining) but incurs a wasteful request when the client doesn't support server-initiated progress. Confidence slightly reduced: this may be intentional since modern VS Code always supports progress.

- `src/providers/WorkspaceIndexingService.ts:211` | Fallback walker enumeration phase has no progress indicator (phase-deferral side effect) | P3 | 0.55 | The F2 fix correctly defers `progress.begin('Indexing G-code files')` to after `collectScanTargets` returns. For the client-enumeration path this is correct (client emits "Finding…" under the shared token). For the fallback walker path (`supportsListIndexFiles === false`), `collectFiles` doesn't emit any progress — so the progress bar now only opens after the file walk completes, giving the user no visual feedback during potentially lengthy directory traversal. Before the fix the label was misleading ("Indexing…" during file discovery) but at least provided activity indication. Confidence reduced: fallback path is legacy; the trade-off is arguably acceptable; `collectFiles` was never instrumented with progress anyway.

- `src/test/providers/WorkspaceIndexingService.test.ts:424` | F2 phase-ordering test doesn't assert `Finding-begin` before `Indexing-begin` in a single test | P3 | 0.55 | The test "defers the indexing-phase begin until after requestFiles resolves" uses a raw `requestFiles` mock and records `['requestFiles:start', 'requestFiles:end', 'begin:Indexing G-code files', 'done']`. No `begin:Finding G-code files` event appears because the mock bypasses `WorkspaceFileEnumerator`. The architecture-mandated invariant (Finding phase visible before Indexing phase) is provable only by composing this test with `WorkspaceFileEnumerator.test.ts:✓ emits $/progress begin before findFiles`. Not a code defect; unit-test boundary is the reason. A future integration test or a combined mock that wraps the enumerator could make this explicit.
